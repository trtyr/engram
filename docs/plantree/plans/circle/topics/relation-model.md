# 实体关系升级（共现 → 语义）候选方案

## 现状

实体间唯一的关系是「共现」：`atom_entities` 自连接，同一原子同时关联两实体 → `count(*) AS weight`。
无方向、无类型、无语义。「张三 ∈ 后端组」「上海 = 长亭科技所在地」都表达不成「关系」，只能表达「常一起出现」。

## 为什么这是 P3（不是 P1/P2）

- 数据密度是前置条件：密度没上来前，关系类型化是空中楼阁（见 data-density.md）。
- 建表是 schema 级改动（迁移 0020+），且关系「谁写、写什么」是产品语义决策，必须用户拍板。

## 三条候选路线

### 路线 A：完整类型化关系表（重）

- 新表 `entity_relations(from_id, to_id, rel_type, weight, source, created_at)`。
- rel_type 枚举（member_of / located_in / works_on / related_to…）。
- 关系来源：蒸馏抽取（LLM 判关系类型）+ 手动建。
- 代价：新 schema + 抽取 prompt 扩展 + 关系维护（矛盾仲裁）+ 图渲染改造（有向边 + 关系标注）。
- 收益：图从「抱团」升级成「有语义的知识图谱」，圈子真正「强大」。

### 路线 B：共现 + 关系摘要折中（轻）

- 保留共现边，但允许给「共现边」附一条关系摘要（LLM 对高频共现对生成一句话关系说明）。
- 不建新表，关系摘要存在现有结构（或轻量 `entity_relations` 只存 summary，不存类型枚举）。
- 代价：小；收益：图能 hover 出「张三 × 后端组：成员」这类说明，但不可按关系类型查询/过滤。

### 路线 C：维持现状 + 画像摘要兜底（最轻）

- 关系语义继续写在实体画像摘要里（e2174fda9b28 的 MVP 取舍）。
- 图只做「共现抱团」的可视化，关系语义靠点进详情读摘要。
- 代价：零；收益：零新增能力。

## 倾向（已拍板）

**A** 已拍板（2026-09-01 用户选 A：完整类型化关系表）。实现：迁移 0021 `entity_relations`（5 类关系枚举 member_of/located_in/works_on/part_of/related_to + 有向 + 同向同类型 upsert）+ 蒸馏 extract 抽取（source=distill）+ 关系 CRUD 路由 + 有向图边。B/C 作为落选方案存档。
