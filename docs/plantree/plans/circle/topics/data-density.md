# 数据密度瓶颈（图的灵魂，先读）

## 现象

圈子图的全部「信息」都编码在密度上：

- 节点大小 = `5 + min(atom_count × 1.1, 9)` —— 记忆条数越多，节点越大。
- 边粗细 = `weight`（同原子共现次数）—— 越常一起出现，线越粗、力导向越抱团。

2026-09-01 审计活体：**16 实体全 atom_count=1、13 边全 weight=1**。结果是图退化成一张「我居中 + 16 个等大节点围一圈 + 全是细线」的均匀星形点名册——没有大小差、没有抱团、没有信息量。

## 根因

不是 bug，是「图的能力 > 当前数据密度」的结构性落差。密度由两件事决定：

1. **蒸馏实体抽取的质量与数量**——一次会话能抽出多少实体、每个实体挂多少原子（extract 的 entity 抽取 + 挂链）。
2. **数据积累时间**——用户真实记忆的厚度。

当前生产数据是测试方重建的（每个实体挂 1 条原子），密度天然低。

## 应对（两难）

- **A. 等数据自然积累**：不做任何事，等用户真实使用 + 蒸馏把密度堆起来。风险 = 用户在数据成熟前打开圈子，看到的是无信息量的星形图，第一印象差。
- **B. 降级过渡**：数据成熟前「列表为主、图为辅」——默认展示密度排序列表，图作为次级视图；密度达标（如 ≥N 个 atom_count>=3 的实体）后再让图当主角。代价 = 增加「密度阈值」判定逻辑。

## 判断

倾向 **B 的轻量版**：不改默认视图，但在**空态/低密度态**加一条诚实提示（如「图谱关系会随记忆积累逐渐成形——现在先看列表」），而不是让用户面对一张死图。这是 P2 的「低密度信息呈现」项，便宜且不伤。

关系升级（P3）也要等密度上来才有意义——先有「谁和谁常一起出现」的数据，才谈得上「他们是什么关系」。
